## Part 1 of 2

Minor, app/controllers/issue_digest_rules_controller.rb:226
Problem: normalize_schedule_config unconditionally clears schedule_config (sets it to {}) whenever schedule_config is nil and the params include schedule_type, regardless of whether the submitted schedule_type actually requires configuration fields. This means an update that includes schedule_type but omits schedule_config (e.g., due to a forged request or a client bug) will drop the existing configuration for types that do require it.
Failure scenario: A user with manage_digest_rules opens Edit, but a proxy/browser glitch posts PATCH with schedule_type='weekly' and no schedule_config (or an attacker crafts such a request). The controller sets schedule_config to {}, wiping any previously saved weekly day setting. If model validations don’t reject empty config for that type (or the model later evolves), the rule may persist with an invalid or unintended schedule. Even with strict validations, the user loses the prior config and is forced to re-enter it.
Fix: Only clear schedule_config when the submitted schedule_type is one of the types that genuinely have no config (e.g., daily, monthly_last_day, manual). For other types, leave schedule_config as nil so the update won’t overwrite the existing config unless new config is provided. Example:
- Define a constant NO_CONFIG_TYPES = %w[daily monthly_last_day manual].freeze
- Change the line to:
  config = {} if config.nil? && permitted.key?(:schedule_type) && NO_CONFIG_TYPES.include?(permitted[:schedule_type].to_s)
This preserves existing configs unless the new type needs none.

Resolution: fixed in the next commit ("Keep the stored schedule config when none is sent"): the config is cleared only for types without config fields (not in SCHEDULE_CONFIG_KEYS); controller spec "keeps the stored config when a type with fields is sent without any" fails without it. Path is a crafted or broken request only (the form always sends the visible block), and model validation would have refused the empty weekly config, but the fix is one condition.
